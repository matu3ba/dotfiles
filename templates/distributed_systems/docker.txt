==usage
docker compose up|down|logs|ps
docker build|ps|pull|push|run|stop

docker compose up
  --abort-on-container-exit, --abort-on-container-failure, --menu [incompat with --detach]
  -d | --detach
  --always-recreate-deps [incompat with --no-recreate]
  --[no-]attach stringArray restrict attaching to specified services [incompat with --attach-dependencies]
  --[no-]build build images before starting containers
  --dry-run
  --exit -code-from string return exit code of selected service container [implies --abort-on-container-exit]
  --force-recreate
  --no-color|deps|log-prefix|recreate|start
  --pull string
  --quiet-build|poull
  --remove-orphans
  -V --renew-anon-volumes recreate anonymous vols instead of retrieving data from prev container
  --scale scale
  -t --timeout int timeout [seconds] for shutdown when attached or already running
  --timetamps | --wait
  --wait-timeout int
  -w | --watch watch source code and rebuild/refresh when files are updated
  -y | --yes assume "yes" answer to all prompts and run non-interactively

docker compose down
      --dry-run | --remove-orphans (containers not defined in compose file)
      --rmi string  remove images used by services, 'local' removes only images without custom tag ('local'|'all')
  -t, --timeout int specify shutdown timeout [s]
  -v, --volumes remove named vols declared in volumes sections of compose file
                and anonymous volumes attached to containers

docker run [options] IMAGE [COMMAND [ARG...]]

docker start [options] CONTAINER [CONTAINER..]
  -all, -a|--attach, --detach-keys [a-Z],
  -f filter stringarray, -i interactive, -l last, --sig-proxy

copy files from running container
docker cp <containerId>:/container_path_source /host_path_target

SHENNANIGAN
docker may have permission problems on directories, debugging steps
id
docker run --rm --entrypoint id quay.io/keycloak/keycloak:26.6.0
More weirdly, it is unable to correctly set permissions for directory volumes, so they may need fixup
# directory volumes (here ./kc_backups) may be owned as root
chmod g+w ./kc_backups
# 1000 is user keycloak in container, group appears to be same on system
docker run --user 1000:$(id -g) --name keycloak-export -v kc_data:/opt/keycloak/data -v ./kc_backups:/kc_backups -p 127.0.0.1:8080:8080 -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin quay.io/keycloak/keycloak:26.6.0 export --dir /kc_backups

Docker doesn't bypass permisisons unless instructed via --privileged or --user root
Note the difference between host bindings to local dirs ./kc_backups and kc_data managed by docker runtime.
* see >docker volume ls

==local_backup (persistent /opt/keycloak/data, backups in kc_backups/)
docker run --name keycloak-run -v kc_data:/opt/keycloak/data -v ./kc_backups:/kc_backups -p 127.0.0.1:8080:8080 -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin quay.io/keycloak/keycloak:latest start-dev
# modify keycloak
docker run --user 1000:$(id -g) --name keycloak-export -v kc_data:/opt/keycloak/data -v ./kc_backups:/kc_backups -p 127.0.0.1:8080:8080 -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin quay.io/keycloak/keycloak:26.6.0 export --dir /kc_backups
==local_restore (persistent /opt/keycloak/data, backups in backups/)
docker run --name kc_restore -v kc_data:/opt/keycloak/data -v ./kc_backups:/opt/keycloak/data/import -p 127.0.0.1:8080:8080 -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin quay.io/keycloak/keycloak:26.6.0 start-dev --import-realm
