==core_ideas
Core ideas of orchestrator Kubernetes
**Purpose** of operating orchestrators is to ensure software availability.
Orchstration is automated configuration, coordination, deployment, management
of computer systems and software.

Bear in mind that Kubernetes is a general orchestrator;
IUPEC/container is just one way to operate applications in contrast to
for example WebAssembly and MicroVMs.

Core ideas of Kubernetes
1. semantic web of deployment and operation of distributed systems
2. control via level-triggered state towards goal state
3. weak transaction guarantees for flexible workload choices
4. weak platform guarantees for flexible platform choices
5. weak default security guarantees to simplify usage
6. accepts bad virtualization and testing experience (no authoritative guide, CI etc)
7. assumes full control of Linux Kernel

==kubernetes
* good at handling relative stateless applications
* bad at handling (very) stateful applications
  - every state recovery [backtrack, checkpoint restore] needs database pass
  - default/optimized to handle stateless applications, so no user-provided state management system
* security: runs in own VPN and applications in pods are isolated; nodes share same security context
  - easy to take over cluster, if pods are compromised
  - there are hard to maintain security solutions on top
  - no custom Kernel/OS architecture enforcing a modern security model, k8 builds on Linux primitives
* reason 1 on demand vertical and horizontal scaling of applications
* reason 2 reduce operator cost by declarative configuration
* tradeoff: no hard latency or time-critical control, no security model (configs + hacks leaving open many attack vectors)
  - security model: each cluster assumes it has its own PN, default Linux containers, no VM
  - https://research.checkpoint.com/2026/voidlink-the-cloud-native-malware-framework/
  - looks like bad things might happen with kubernetes, docker
    => dependency attacks very common
    => point of security tools to prevent access escalation (and follow-up)
    and communication to web (with follow-up)
    => Kubernetes/docker have weak tools to do that,
    so attack frameworks might become very lucrative.

==kubernetes_deployments
https://www.groundcover.com/blog/kubernetes-deployment-strategies
1. Recreate deployment
* delete all the existing pods before creating new pods
* need all application instances to run the same application version at all times
* advantage: same application versions at all times
2. Rolling deployment
* default deployment strategy
* manages pod updates by applying them incrementally to each pod instance
* advantage: other instances remain available to handle requests (zero downtime)
* readiness probe helps ensure updated pods are ready before older ones are removed
* disadvantag: slow switchover and rollback
3. Blue/green deployment
* two distinct Kubernetes deployments – a blue deployment and a green one – and switch traffic
  between them so the new version takes over only after the old version has been verified
  it works properly before directing traffic to it
* advantage:
  - allows you to test one version of your deployment and confirm that
  - sudden switchover and rollback
* disadvantag: high infra cost
4. Canary deployment
* gradual traffic switching between distinct deployments
* advantage
5. A/B testing deployment
6. Shadow deployment
7. Best-effort controlled rollout
8. Ramped slow rollout

https://www.ionos.at/digitalguide/server/konfiguration/kubernetes-deployment/

Zero-downtime deployments https://dixken.de/blog/kubernetes-deployment-strategies
1. Rolling Updates, created above desired count(maxSurge),
   unavailable during update(maxUnavailable)
2. Blue-Green Deployments to switch traffic from old(blue) to new(green) version
   after validation
3. Canary Releases, gradually rollout to users before available to everyone
Best Practices
1. Health Checks: Readiness and liveness probes.
2. Resource Limits: Resource exhaustion prevention.
3. Monitor Rollouts: Progress tracking and automate rollbacks.
4. Test Thoroughly: Staging validation before production.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-deployment
  namespace: namespace1
spec:
  # default replicas:1, type:RollingUpdate
  replicas: 1
  strategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: app1 # Findet die Pods unten
  template:
    metadata:
      labels:
        app: app1
    spec:
      containers:
      - name: web-container
        image: docker.io/library/nginx:alpine
        ports:
        - name: http-web # "Named Port" in Pod
          containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: app-service1
  namespace: namespace1
spec:
  type: ClusterIP
  selector:
    app: app1 # refers to pod labels above
  ports:
  - name: service-http
    port: 8080           # Port to make service intern reachable
    targetPort: http-web # maps on Named Port of Pods
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app-route1
  namespace: namespace1
spec:
  parentRefs:
  - name: shared-gateway # uses existing Gateway
    namespace: infra-namespace
  hostnames:
  - "app1.beispiel.de"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: app-service1
      port: 8080 # Nutzt den Port des Services
---
